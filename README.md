# int8rt: INT8 inference runtime with an accelerator cost model

A small Python and NumPy runtime that executes INT8-quantised ONNX models and aims to match ONNX Runtime (ORT) on CPU byte
for byte. On top of it sit a static activation memory planner and an analytical cost model for a generic accelerator.
Correctness first, then memory, then performance modelling.

## What this is, and is not

**Is:**
- A pure NumPy runtime (explicit integer dtypes, INT32 accumulation, no torch / scipy / ORT inside `int8rt/`) for a
  static-shape, batch-1 subset of QOperator-format INT8 ONNX models. ORT is used only as the reference.
- Two requantisation modes: **float** (Mode A, float32 multiply and round-half-even, bit-exact with ORT 1.31.1 on both
  models here) and **fixed-point** (Mode B, INT32 multiplier plus shift, gemmlowp-style, integer-only). Mode B deviates
  from ORT by design; the deviation is measured below.
- A static activation memory planner (liveness, greedy-by-size arena of real NumPy views).
- An analytical cost model (`costmodel/`) for a *configurable, generic* accelerator: MAC array, two SRAMs, DMA, vector unit.

**Is not:**
- Not fast. Host CPU time is incidental; nothing here is a performance claim about the NumPy code.
- Not a general ONNX runtime or compiler: no dynamic shapes, no training, no GPU, no threading, no C++.
- Not a model of any real company's chip. Every accelerator parameter is an assumption. Modelled cycles are not measured
  cycles, and they are kept apart from numerical results everywhere in this repo.

Three kinds of numbers are used and always labelled: **numerical correctness** (vs ORT), **modelled** accelerator cost,
and **measured** host CPU time (only in the JSON files, never used as a claim).

## Supported ops

Exactly the ops that appear in the two target models after `quantize_static` (`tools/list_ops.py`, `results/ops_cifar.txt`),
plus `QLinearMatMul`, which the spec lists. Anything else is rejected by the importer with an error that lists it.

| op (domain) | in CIFAR CNN | in KWS DS-CNN | notes |
| --- | :---: | :---: | --- |
| QuantizeLinear (ai.onnx) | yes | yes | per-tensor, divides by scale like ORT |
| DequantizeLinear (ai.onnx) | yes | yes | per-tensor |
| QLinearConv (ai.onnx) | yes | yes | per-channel weights, groups (depthwise), padding, strides; dilation 1 only |
| QGemm (com.microsoft) | yes | yes | per-channel weights, `alpha`, `transA`, `transB`; INT8 output only |
| QLinearMatMul (ai.onnx) | no | no | 2-D only; covered by single-op tests |
| QLinearGlobalAveragePool (com.microsoft) | yes | no | NCHW only |
| MaxPool (ai.onnx) | yes | no | no ceil_mode, dilation or auto_pad |
| Flatten (ai.onnx) | yes | no | |
| ReduceMean (ai.onnx) | no | yes | trailing contiguous axes only (reproduces ORT's float32 summation order, MISMATCHES M-001) |

Not implemented because neither model uses them: QLinearAdd, QLinearAveragePool, Reshape, N-D QLinearMatMul, dilation other
than 1, `auto_pad`. See the stretch-goal note under Limitations.

## Install

Python 3.10+ (developed and tested on 3.12.10, Windows 11; CI uses 3.12 on Linux). Versions are pinned exactly in
`requirements.txt`, and ORT parity is defined against the pinned `onnxruntime`.

```bash
python -m venv .venv
. .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install -e . --no-deps
```

`torch` and `torchvision` are used only to train / export the CIFAR model and to read the CIFAR-10 test set; on Linux the
default wheel is large, and `pip install --extra-index-url https://download.pytorch.org/whl/cpu -r requirements.txt` (as CI
does) gives the CPU build.

## Test

```bash
ruff check .
mypy
pytest -q
```

`models/` and `data/` are git-ignored and regenerated by the scripts below. On a fresh clone the tests that need a trained
model are **skipped** (they say so), and everything else, including all kernel, requantisation, planner and cost-model
tests, runs. After generating the models (next section) the skipped tests run as well.

## Reproduce the models and results

Each script writes to `results/` with date, git commit, CPU, OS, Python and package versions and its exact command.

```bash
# CIFAR-10 CNN: train (downloads CIFAR-10 to data/), export to ONNX, quantise, list ops
python -m tools.train_cifar_cnn --epochs 8
python -m tools.export_quantize --arch cifar
python -m tools.list_ops models/cifar/cifar_int8.onnx -o results/ops_cifar.txt

# KWS DS-CNN comes from Project 2 (not in this repo). Copy dscnn_int8.onnx, dscnn_fp32.onnx,
# kws_test_features.npz and SOURCE.json (records the Project 2 commit) into models/kws/kws/

python -m tools.make_op_tests                      # 300 single-op cases vs ORT
python -m tools.compare_ort --model cifar          # per-layer + whole-test-set parity, accuracy, Mode B
python -m tools.compare_ort --model kws
python -m tools.run_memory_report --model cifar    # also --model kws
python -m tools.run_cost_model --model cifar       # also --model kws
python -m tools.make_readme_tables                 # rebuild the results section below
```

## Use

```bash
python -m int8rt run --model models/cifar/cifar_int8.onnx --input x.npy --output y.npy \
    [--requant float|fixed] [--planner naive|greedy] [--dump-all DIR]
python -m int8rt memreport --model models/cifar/cifar_int8.onnx     # naive / planned / lower bound, JSON
```

```python
from int8rt.importer import load_model
from int8rt.executor import Executor

ex = Executor(load_model("models/cifar/cifar_int8.onnx"), requant="float", planner="greedy")
outputs = ex.run({"input": x})  # x: float32 (1, 3, 32, 32)
```

## Limitations

- **Parity scope.** Float mode is bit-exact with ORT 1.31.1 CPU on the two models here and on 300 single-op cases. That is
  evidence for these ops and shapes, not a proof for others. Per-layer parity covers the first 100 test inputs per model;
  the final logits are compared on every test input.
- **ORT behaviour reproduced empirically.** ReduceMean matches only because int8rt copies ORT/Eigen's float32 summation
  order, and only for trailing contiguous axes (and a 16-byte-aligned buffer). Other axis patterns are rejected.
  See `docs/MISMATCHES.md`.
- **Fixed-point mode deviates** from ORT by up to 1 LSB per node in isolation and compounds (see table 4). I suspect, but have
  not tested, that GAP's larger deviation comes from round-half-up vs round-half-even on exact ties.
- **Planner.** Greedy-by-size equals the lower bound on both models, but both are straight chains, so this says little about
  branchy graphs. No in-place reuse, no Flatten aliasing. Weights and the NumPy im2col scratch are outside the arena.
- **Cost model.** Layers are modelled in isolation (every layer's input and output goes through DRAM), which probably
  overstates how many layers are transfer-bound. No DRAM latency, halo re-fetch, array fill/drain, or energy. The
  no-overlap column reuses the double-buffer-optimal tiling, so "DMA stalls cut" is an upper estimate. My reading of the
  spec's double-buffering formula differs slightly from its wording (`docs/DESIGN.md` D27). Absolute cycle counts are not
  hardware predictions; the trends are the defensible part.
- **Models.** The CIFAR CNN is a small net trained for 8 epochs (about 77% accuracy); it exists to exercise the runtime.
  The KWS model and its test features come from Project 2 and are not stored here, so a fresh clone cannot reproduce KWS results
  without them.
- **CI.** `.github/workflows/ci.yml` runs ruff, mypy and pytest, but this repo has no GitHub remote yet, so CI has never run.
  The same three commands pass locally.
- **Stretch goal not done.** MobileNetV2 would need QLinearAdd, QLinearAveragePool and more; it was optional and I did not add
  it, because it widens scope.

## What did not work (first attempts)

- `np.sum` for ReduceMean: 19 of 25 ORT comparisons failed until Eigen's summation order was copied (M-001).
- Random single-op tests alone could not distinguish the float32 multiplier orders; a 6,000,000-accumulator sweep through
  ORT's requantiser was needed (`results/ort_probe.json`).
- Largest-tile-that-fits for vector layers in the cost model made bigger SRAMs look slower; they now search tile counts like GEMMs (DESIGN D29).
